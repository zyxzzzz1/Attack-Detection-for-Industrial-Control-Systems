## 3. Data overlap between files (train and test contain the same data)

### Method

- For every row of every file, take only the 79 sensor columns (not `time` or the label columns), convert them to float64 and compute a 64-bit row hash (`src/utils/rowhash.py`).
- All 8 files are compared pairwise (28 pairs: train×test, train×train, test×test), finding rows with identical hashes and merging rows whose indices increase together on both sides into contiguous runs.
- The comparison does not depend on timestamps, so shifted partial overlaps are found too; duplicated rows within each file are counted as well.

### Results

| File A | Position in A | Time in A | File B | Position in B | Time in B | Identical rows | Timestamps aligned |
|---|---|---|---|---|---|---|---|
| train1 (train) | first 1 rows | 2020-07-11 00:00:00 ~ 2020-07-11 00:00:00 | test2 (test) | last 1 rows | 2020-07-11 00:00:00 ~ 2020-07-11 00:00:00 | 1 | yes |
| train1 (train) | last 43201 rows | 2020-07-13 00:00:00 ~ 2020-07-13 12:00:00 | test3 (test) | first 43201 rows | 2020-07-13 00:00:00 ~ 2020-07-13 12:00:00 | 43201 | yes |

- 2 of the 28 file pairs share rows with identical content; none of the other 26 pairs share a single row.
- By type: train×test 2 pairs, train×train 0 pairs, test×test 0 pairs.
- Overlapping runs shifted in time: 0.
- Rows with duplicated content within a file: train1 0, train2 0, train3 0, test1 0, test2 0, test3 0, test4 0, test5 0.
- In total 43202 rows are identical between train and test; attack events intersecting these rows: 0 (the overlap is entirely normal data).

### Impact and handling

- Impact: if left alone, the model would already have seen this normal test data during training, the reconstruction error for those periods would be too low, and the false-alarm rate would be underestimated.
- Principle: **no test row may appear in the training data, not even one.** So besides the last 43,201 rows of train1, row 1 of train1 (identical to the last row of test2) is removed as well.
- Handling: **rows identical to test are removed from the training set; test stays exactly as officially released** (implemented in M1, config switch on by default). Constant columns are determined and the scaler fit after the removal; the removed rows are at the head or tail of a train file, so no new internal boundary appears.
- Status: implemented in M1 (`ml.data.drop_train_overlap` on by default; `ml.data.train_overlap_drops` is head_rows 1, tail_rows 43201 for train1). Both removals confirmed (2026-10-07).
- Verification: the M1 tests assert by content hash that no training window contains any test row.
- Cited in the report: the data section states where and how many rows were removed; the limitations section states that the official train/test release contains duplicates, so results are not fully comparable with publications that did not do this.
