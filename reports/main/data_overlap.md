# Data overlap between train1 and test3 in HAI 21.03

The official HAI 21.03 release contains the same data in a training file and a test file. This note records where the
overlap is, how it was found, how this project handles it and what it means for evaluation. The source is section 3 of
[`data_summary.md`](data_summary.md) (in Chinese, generated by `python -m scripts.hai_data_summary`); the numbers below
are taken from it.

## Location and row counts

One row is one second.

| Training file | Position | Time | Test file | Position | Time | Identical rows | Timestamps aligned |
|---|---|---|---|---|---|---|---|
| train1 | last 43,201 rows | 2020-07-13 00:00:00 to 2020-07-13 12:00:00 | test3 | first 43,201 rows | 2020-07-13 00:00:00 to 2020-07-13 12:00:00 | 43,201 | yes |
| train1 | first 1 row | 2020-07-11 00:00:00 | test2 | last 1 row | 2020-07-11 00:00:00 | 1 | yes |

- train1 has 216,001 rows and test3 has 108,001 rows, so the overlap is the last 12 hours of train1 and the first 12
  hours of test3.
- In total 43,202 rows are shared between train and test.
- No attack event intersects these rows: the shared data is all normal operation.
- Of the 28 file pairs, these 2 contain identical rows. The other 26 pairs share no row. There is no overlap between
  two training files or between two test files, and no file contains internally duplicated rows.

## Detection method

- For every row of every file, take only the 79 sensor columns (not `time`, not the label columns), convert them to
  float64 and compute a 64-bit row hash (`src/utils/rowhash.py`). The conversion matters because the same column can be
  parsed as int64 in one file and float64 in another.
- Compare all 8 files pairwise (28 pairs: train × test, train × train, test × test), find rows with equal hashes, and
  merge rows whose indices advance together on both sides into contiguous runs.
- The comparison does not use timestamps, so an overlap shifted in time would also be found. None was: both runs are
  aligned in time.

## Handling

- Principle: no test row appears in the training data, not even one.
- The overlapping rows are removed from the training set: the last 43,201 rows and the first 1 row of train1. The test
  files are kept exactly as released.
- Configuration: `ml.data.drop_train_overlap` (on by default) and `ml.data.train_overlap_drops` (train1: `head_rows: 1`,
  `tail_rows: 43201`) in `config/config.yaml`. The drops are described as row counts at the head and tail of a file, so
  the training pipeline does not read any test file.
- Constant columns are determined and the scaler is fitted after the removal. The removed rows are at the start and end
  of a file, so no new internal boundary is created.
- After the removal the training data has 878,401 rows (921,603 − 43,202): train 702,721, val_es 87,840 and val_thr 87,840.
- Check: `tests/test_preprocess.py::test_real_training_windows_contain_no_test_rows` asserts by content hash, not by
  timestamp, that no training window contains a test row. It runs where the full dataset is available.

## Effect on evaluation

- Without the removal, the first 12 hours of test3 would be normal data the model had already seen in training.
  Reconstruction error there could be lower than on unseen data, and the false alarm rate on test3 could be understated.
- The size of this effect was not measured: no model was trained with the overlap left in.
- The affected rows contain no attack, so the removal does not change which attacks are evaluated. All 402,005 test
  seconds and all 50 attack events are still evaluated.
- Results from work that trains on the official files unchanged are not strictly comparable with the results here.
